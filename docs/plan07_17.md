## 一、Bug 修复（优先级：高）

### Bug 1：顶部标题栏显示 `[object Object]`

**位置**：`src/App.tsx`（以及所有错误捕获处）

**根因分析**：

`App.tsx` 中所有 `catch` 块都使用以下模式设置错误消息：

```ts
setBackendError(error instanceof Error ? error.message : String(error));
```

在 Tauri 环境中，`invoke()` 失败时抛出的错误**不是** JS `Error` 实例，而是一个普通对象，形如：

```ts
{ code: "not_found", message: "..." }
```

对这样的对象调用 `String(error)` 会返回 `"[object Object]"`，而不是实际错误信息。

由于 `backendError` 显示在 `topbar`（顶部标题栏区域），用户会看到 `[object Object]`。

**修复方案**：

在 `src/lib/api.ts`（或单独的 `src/lib/errors.ts`）中添加统一的错误格式化函数：

```ts
export function formatError(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (error && typeof error === "object") {
    const obj = error as Record<string, unknown>;
    if (typeof obj.message === "string" && obj.message) return obj.message;
    if (typeof obj.code === "string") return `Error [${obj.code}]`;
  }
  return String(error);
}
```

然后将 `App.tsx` 中所有 `error instanceof Error ? error.message : String(error)` 替换为 `formatError(error)`，同时检查 `src/components/` 下其他组件的错误处理。

**涉及文件**：
- `src/lib/api.ts`（添加 `formatError` 导出）
- `src/App.tsx`（替换全部7处错误捕获）
- `src/components/ProviderModal.tsx`（`formError` 设置处）
- `src/components/ManagementPages.tsx`（如有错误处理）

### Bug 2：供应商测试连接 / 同步模型瞬间失败

**位置**：
- `src/components/ProviderModal.tsx`（`testConnection`、`syncModels`）
- `src-tauri/src/commands.rs`（`adapter_for_profile`）

**根因分析**：

调用链如下：

```
ProviderModal.testConnection()
  → prepareDraft()           # 将 apiKey 存入系统 keyring，返回 apiKey="" 的 provider
  → api.testProvider(provider) → invoke("provider_test", { provider: {apiKey: ""} })
    → Rust adapter_for_profile(&state, &provider)
      → state.secret(credential_key()).await?  # 从 keyring 取回 apiKey
```

**已知问题点**：

1. **Windows Keyring 访问失败**：`keyring` crate 在部分 Windows 配置下（企业策略、UAC 限制、MSIX 打包签名问题）无法访问 Windows Credential Manager，`state.secret()` 立即返回 `Err`。

2. **错误信息被吞掉**：当前 `testConnection` 的 catch 块只做 `setTestState("failure")`，不展示任何错误信息，导致用户看到的是"瞬间失败"而不知道原因。

3. **`[object Object]` 掩盖真正错误**（与 Bug 1 叠加）：即使有错误信息，显示也是乱码。

**修复方案**：

**A. 短期修复（展示真实错误）**：

在 `ProviderModal.tsx` 中，修改 `testConnection` 和 `syncModels` 以展示具体错误：

```ts
const testConnection = async () => {
  setTestState("testing");
  setFormError("");
  try {
    const provider = await prepareDraft();
    setTestState((await api.testProvider(provider)) ? "success" : "failure");
    if (testState() === "failure") setFormError(props.t("connectionFailed"));
  } catch (error) {
    setTestState("failure");
    setFormError(formatError(error)); // 显示真实错误，而非空白
  }
};
```

**B. 根本修复（避免 keyring 依赖）**：

在 `testConnection` 和 `syncModels` 中，如果用户当前在输入框中填写了 `apiKey`，则直接将其随请求传递，不依赖 keyring 查找。修改 `prepareDraft` 或新建 `prepareForTest` 函数，在返回的 provider 中保留原始 `draft.apiKey`（不清空）用于 test/sync 场景：

```ts
// ProviderModal.tsx
const testConnection = async () => {
  setTestState("testing");
  setFormError("");
  try {
    const provider = await prepareDraft();
    // 将当前输入框中的 apiKey 直接传入，不依赖 keyring
    const providerForTest = { ...provider, apiKey: draft.apiKey };
    setTestState((await api.testProvider(providerForTest)) ? "success" : "failure");
  } catch (error) {
    setTestState("failure");
    setFormError(formatError(error));
  }
};
```

`api.testProvider` 中，修改 `sanitizeProviderForCommand` 逻辑：当 `provider.apiKey` 非空时保留它（让 Rust 端优先用传入的 key，而非 keyring）：

```ts
// Rust adapter_for_profile 已有此逻辑：
// let api_key = if profile.api_key.trim().is_empty() {
//     state.secret(profile.credential_key()).await?  // keyring
// } else {
//     profile.api_key.trim().to_owned()  // 直接使用
// };
```

Rust 端已正确支持"优先用传入的 key"，所以只需前端不清空即可。

**C. 同步模型同理**：同样保留 `apiKey`。

**涉及文件**：
- `src/components/ProviderModal.tsx`
- `src/lib/api.ts`（`testProvider`、`syncModels` 函数中移除多余的 `sanitizeProviderForCommand` 或修改其行为）

### 4. API Key 保存后显示为星号提示

**位置**：`src/components/ProviderModal.tsx`（第 282–284 行）

**问题**：当前保存 API Key 后，输入框为空（`apiKey: ""`），虽然有 `placeholder="已保存凭据"` 但不直观，用户感觉没有输入过 Key。

**修复方案**：

当 `draft.hasStoredSecret === true` 且 `draft.apiKey === ""` 时，用 `value` 显示伪装的星号字符串 `"••••••••••••"` 并在 `onFocus` 时清空，让用户可以重新输入：

```tsx
// ProviderModal.tsx - API Key Field
<Field label={props.t("apiKey")} required class="span-2">
  <input
    type="password"
    value={draft.hasStoredSecret && !draft.apiKey ? "••••••••••••" : draft.apiKey}
    autocomplete="off"
    spellcheck={false}
    placeholder={draft.hasStoredSecret ? props.t("credentialSaved") : ""}
    onFocus={(event) => {
      // 清空伪星号，让用户重新输入
      if (draft.hasStoredSecret && !draft.apiKey) {
        event.currentTarget.value = "";
      }
    }}
    onInput={(event) => setDraft("apiKey", event.currentTarget.value)}
  />
</Field>
```

**注意**：`type="password"` 下，`value="••••••••••••"` 会被浏览器渲染为黑点，视觉效果符合预期。

**涉及文件**：`src/components/ProviderModal.tsx`

### 5. 历史记录页日期筛选按钮无作用

**位置**：`src/components/ManagementPages.tsx`（第 113 行）

**问题**：`"最近30天"` 按钮没有 `onClick` 处理函数，点击无效。

**修复方案**：

添加 `dateFilter` 信号，实现筛选逻辑：

```tsx
// 添加信号
const [dateFilter, setDateFilter] = createSignal<"all" | "30d" | "7d">("all");

// 修改 records memo 加入日期过滤
const records = createMemo(() => {
  const cutoff = dateFilter() === "30d"
    ? new Date(Date.now() - 30 * 86400_000)
    : dateFilter() === "7d"
    ? new Date(Date.now() - 7 * 86400_000)
    : null;

  return props.history
    .filter((record) => record.projectId === props.project.id)
    .filter((record) => !cutoff || new Date(record.createdAt) >= cutoff)
    .filter((record) => providerId() === "all" || record.providerId === providerId())
    .filter((record) => status() === "all" || record.status === status())
    .filter((record) => model() === "all" || record.model === model())
    .filter((record) => `${record.prompt} ${record.model}`.toLowerCase().includes(query().toLowerCase()));
});

// 按钮改为可切换状态
<button
  class={`button ${dateFilter() !== "all" ? "primary" : "secondary"}`}
  type="button"
  onClick={() => setDateFilter(dateFilter() === "30d" ? "all" : "30d")}
>
  <CalendarDays size={16} />
  {dateFilter() === "30d" ? props.t("last30Days") + " ✓" : props.t("last30Days")}
</button>
```

可选：扩展为下拉菜单（全部时间 / 最近7天 / 最近30天）。

**涉及文件**：`src/components/ManagementPages.tsx`

## 三、功能改进（优先级：中）

### 6. 生图请求默认使用流式 API，失败时回退同步

**问题**：`initialDraft.stream = false`，所有请求使用同步 API。图片生成耗时长（10–60 秒），同步 API 超时概率高，导致请求失败但无法获取结果。

**方案概述**：

**A. 前端默认开启 streaming**

修改 `src/data/demo.ts` 中 `initialDraft`：
```ts
stream: true,  // 改为 true
```

修改 `src/lib/prompt.ts` 的 `normalizeDraftForModel`，确保不支持流式的模型自动重置为 `false`：
```ts
stream: capabilities.supportsStreaming ? draft.stream : false,
```

**B. Rust 端执行逻辑确认**

`executor.rs` 中 `execute_realtime` 已根据 `prepared.provider_request.stream` 决定是否使用 SSE。`openai.rs` 的 `execute_images` 接受 `stream: bool` 参数，流式模式下会在 body 中插入 `"stream": true`。

**需要验证**：`prepare_generation_request`（`mapping.rs`）是否将 `draft.stream` 正确传递到 `provider_request.stream`。如果没有，需要在 `mapping.rs` 中补充：

```rust
// 在 provider::GenerationRequest 构建处
stream: request.draft.stream,
```

**涉及文件**：
- `src/data/demo.ts`（`initialDraft.stream = true`）
- `src/lib/prompt.ts`（`normalizeDraftForModel` 中添加 `stream` 归一化）
- `src-tauri/src/runtime/mapping.rs`（确认 `stream` 字段传递正确）
- `src-tauri/src/runtime/executor.rs`（确认 `execute_realtime` 使用 `stream` 标志）

**注意**：流式请求需要 API 端点支持。DALL-E 2 不支持流式，需在 capabilities 中确认已标记 `supportsStreaming: false`。
